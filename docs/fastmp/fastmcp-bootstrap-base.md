# FastMCP 빌드업 부트스트랩 기능 설계도

> **목적:** 기존 서비스의 MCP를 연결하고, 필요한 도구를 선별해 노출하며, 실제 호출까지 가장 짧은 경로로 검증한다.
>
> **설계 기준:** 프레임워크 기능을 조합하고, 용도별 차이는 연결 정보와 정책으로 표현한다. 추가 코드는 기본 기능으로 충족되지 않는 요구에만 사용한다.

## 1. 무엇을 구성하는가

FastMCP를 **MCP 클라이언트와 하나 이상의 MCP 서버 사이의 Gateway**로 사용한다. 서비스의 기능은 연결된 MCP가 제공하고, Gateway는 그 기능을 발견·식별·노출·중계한다. `ProxyProvider`가 이 연결과 컴포넌트 중계를 담당한다. [1]

| 구성 층 | 역할 | 빌드업할 때 결정할 것 |
|---|---|---|
| 프레임워크 기능 | MCP 통신, provider, namespace, 검색 transform, middleware | 요구에 맞는 기본 기능의 조합 |
| 용도별 구성 | 연결 대상, 도구 노출 범위, 클라이언트 접속 방식 | 실제 서비스 정보와 사용자 작업에 맞는 정책 |
| 선택 확장 | 추가 기록, 도구 제한, 외부 접속 | 해당 요구가 있을 때 적용할 기능과 검증 기준 |

**재사용의 단위는 특정 프로젝트의 파일 묶음이 아니라, 이 기능 조합과 검증 순서다.**

## 2. FastMCP 중심 연결 구성

```text
MCP 클라이언트
      ⇅
클라이언트가 지원하는 MCP 접속 방식
      ⇅
┌─────────────────────────────────────┐
│           FastMCP Gateway           │
│                                     │
│ 도구 노출 정책 · 검색 · 호출 진입점 │
│                  ⇅                  │
│      namespace · 도구별 라우팅      │
│                  ⇅                  │
│    MCP별 ProxyProvider / Client     │
└─────────────────────────────────────┘
           ⇅                   ⇅
         stdio          Streamable HTTP
           ⇅                   ⇅
      로컬 MCP 서버      별도로 실행 중인 MCP 서버
           ⇅                   ⇅
      서비스 또는 도구      서비스 또는 도구
```

Gateway의 **클라이언트 쪽 접속 방식**과 **연결 MCP 쪽 transport**는 따로 선택한다. 예를 들어 클라이언트에는 HTTP로 제공하면서, 연결 대상 중 일부는 stdio로 사용할 수 있다. [1]

| 연결 대상의 형태 | 연결 구성 |
|---|---|
| 명령으로 시작하고 표준 입출력으로 통신하는 MCP | stdio transport에 실행 명령과 실행환경을 지정 |
| 이미 MCP endpoint를 제공하는 서버 | Streamable HTTP transport에 endpoint와 필요한 인증을 지정 |
| 내부에 bridge가 필요한 서비스 | Gateway는 MCP 서버에 연결하고, MCP 서버가 서비스 내부 bridge와 통신 |
| Gateway에 직접 도달할 수 없는 클라이언트 | 해당 클라이언트가 지원하는 인증된 외부 접속 경로를 연결 계층으로 사용 |

**책임 경계:** Gateway는 MCP 접속을 구성한다. 서비스 본체의 준비는 해당 서비스 쪽 책임이다. stdio 접속에 필요한 MCP 자식 프로세스 생성은 transport의 일부로 구분한다.

## 3. 핵심 기능과 조합 규칙

### 3.1 기본 기능 블록

| 기능 | 활용할 FastMCP 기능 | 구성 규칙 |
|---|---|---|
| MCP 연결·통합 | `ProxyProvider`, client, transport | 연결 대상별 접속 정보와 인증을 명시 |
| 도구 자동 discovery | Provider가 가져오는 도구 정의 | 이름·설명·입력 스키마를 원본 MCP에서 받음 |
| 이름 충돌 방지 | `Namespace` 또는 provider namespace | 연결 대상별 고유 namespace를 부여 |
| 직접 노출 | 기본 tool listing | 필요한 도구 정의를 클라이언트에 그대로 제공 |
| 검색형 노출 | Tool Search transform | 직접 노출할 도구와 검색할 도구를 나눔 |
| 호출 중계 | ProxyProvider의 호출 경로 | Gateway의 도구 이름을 원본 도구로 연결하고 결과를 반환 |
| 요청 처리 기록 | Middleware, lifespan 확장점, 로거 | Gateway 처리와 upstream 통신을 구분해 기록 |

Provider·namespace·검색 transform은 프레임워크 기능으로 조합한다. [1][2][3] 로깅의 형식과 실제 upstream 기록 범위는 구성 요구에 맞춰 결정한다. Gateway middleware만으로 실제 upstream 송수신까지 모두 기록된다고 가정하지 않는다. [5]

### 3.2 적용 규칙

**서버 등록과 도구 discovery를 구분한다.** 연결할 MCP와 접속 정보는 구성자가 지정한다. 등록된 서버가 제공하는 도구 정의는 discovery로 가져온다. 서버 목록을 명시하는 일과 도구 스키마를 수작업으로 복제하는 일은 다르다.

**인스턴스별 실행환경과 설정을 독립시킨다.** 의존성은 재현 가능한 조합으로 고정하고, 각 인스턴스가 사용할 연결 정보·로그 목적지를 구분한다. 실행환경 분리는 서비스 접근 권한의 격리를 대신하지 않는다.

**정책은 namespace 적용 후의 이름을 기준으로 정한다.** 직접 노출·제한 목록과 클라이언트가 호출하는 이름이 같은 식별 체계를 사용해야 한다. [2]

**통신 호환성은 연결 대상에 맞춘다.** 실제 지원 transport와 프로토콜로 discovery와 호출을 확인한다. 여러 호출에 걸쳐 상태를 사용하는 MCP는 세션 유지 요구도 함께 확인한다.

## 4. 도구 노출을 선별하는 방법

### 4.1 두 가지 노출 방식

| 방식 | 구성 | 선택 기준 |
|---|---|---|
| 직접 노출형 | 허용된 도구를 기본 목록으로 제공 | 도구 정의의 양이 작고 직접 선택이 충분한 경우 |
| 선별 노출형 | 자주 쓰는 도구 + `search_tools` + `call_tool` | 전체 정의를 매번 제공하기보다 필요한 도구만 찾는 편이 유리한 경우 |

선별 노출형에는 `always_visible`로 직접 노출 대상을 지정한다. 검색 transform이 `search_tools`와 `call_tool`을 제공하며, 검색 결과에는 호출에 필요한 입력 스키마가 포함된다. [3]

### 4.2 선별 노출형의 계약

| 도구 구분 | 초기 도구 목록 | 검색 결과 | 호출 경로 |
|---|---|---|---|
| **Public: 직접 노출** | 포함 | 기본 검색에서는 중복 방지를 위해 제외 | 원래 도구 이름으로 직접 호출 |
| **Searchable: 검색 후 사용** | 원본 정의는 숨김 | 질의와 결과 수 제한에 따라 포함 | 검색 결과의 이름·스키마를 사용해 `call_tool`로 호출 |
| **Restricted: 명시적으로 제한** | 제외 | 제외 | 제한 정책에 따라 호출 거부 |

Public은 여기서 **초기 도구 목록에 표시한다는 뜻**이며, 인증 없는 공개 서비스를 뜻하지 않는다. Searchable도 접근 권한을 제한하는 분류가 아니다. 검색에서 숨겨진 원본 도구는 이름을 알고 있으면 직접 호출할 수 있다. [3][6]

```text
허용 도구       = discovery 결과에 접근·제한 정책을 적용한 집합
직접 노출 도구  = 허용 도구 중 Public으로 선택한 도구
검색 후보       = 허용 도구 중 직접 노출하지 않은 도구
초기 도구 목록  = 직접 노출 도구 + search_tools + call_tool
```

제한 요구가 있을 때는 `Visibility` 등으로 해당 도구를 비활성화하고, 직접 호출과 검색·간접 호출에서 같은 제한이 적용되는지 검증한다. [4][6]

### 4.3 검색과 Public 선정 기준

검색은 필요한 동작을 설명하고 관련도 순서가 유용하면 `BM25SearchTransform`, 이름이나 패턴으로 찾는 것이 적합하면 `RegexSearchTransform`을 선택한다. BM25는 용어 기반 관련도 검색이므로 실제 도구 설명에 맞는 질의로 시험한다. [3]

Public 후보는 **반복 사용 빈도가 높고, 다른 작업의 시작점이 되며, 현재 실행 형태에서 실제 사용할 수 있는 도구**로 좁힌다. 사용 빈도가 불명확하면 소수의 후보로 시작한다.

효율은 초기 목록 크기만으로 판단하지 않는다. **검색 단계의 왕복과 검색 결과의 스키마 크기까지 포함한 전체 호출 비용**을 비교한다. 검색 결과 수 역시 실제 작업에 필요한 범위에서 정한다.

## 5. 실제 호출 워크플로

### 직접 노출된 도구

```text
클라이언트가 도구 선택
→ 입력 스키마에 맞는 인자 전달
→ Gateway에서 도구 해석·정책 적용
→ 해당 ProxyProvider가 원본 MCP에 호출 전달
→ 서비스 실행 결과 반환
```

### 검색 후 사용하는 도구

```text
클라이언트 → search_tools
→ 허용된 검색 후보에서 도구 정의 반환
→ 클라이언트가 반환된 이름·입력 스키마 확인
→ call_tool에 name과 arguments 전달
→ 직접 호출과 같은 도구 처리 경로로 실행
→ 서비스 실행 결과 반환
```

`call_tool`은 별도의 실행 권한을 부여하는 통로가 아니라, 클라이언트에 노출된 공통 실행 진입점이다. FastMCP의 기존 도구 처리 경로로 호출을 전달한다. [6]

**확인해야 할 결과는 세 단계다:** MCP에 연결됐는가, 도구 호출이 프로토콜상 완료됐는가, 실제 서비스 작업이 성공했는가. 응답 상태 하나만으로 세 단계를 모두 성공했다고 판정하지 않는다.

## 6. 로그와 선택 부가 기능

### 6.1 기본 기록 설계

로그는 두 논리 범주로 구성한다. 실제 저장 형식과 위치는 구현 시 정한다.

| 범주 | 기록할 대상 |
|---|---|
| FastMCP 자체 기록 | 시작·종료, 설정 오류, Gateway 요청 처리, 예외 |
| FastMCP ↔ MCP 통신 기록 | 대상 MCP, RPC 메서드, 원본 도구 이름, 요청·결과, 소요시간, 오류 상태 |

공통 필드는 **시각·대상·작업·결과**로 정하고, 여러 구간을 연결해야 하면 상관 식별자를 추가한다. 실제 도구 이름이 확인되어야 하며, 공통 진입점인 `call_tool` 이름만 남겨서는 충분하지 않다.

Gateway 내부 처리, 연결 시도, 실제 upstream RPC를 구분한다. 캐시에서 처리된 조회를 upstream 전송으로 세지 않는다. 통신 기록은 요청·결과의 요약이며 전체 데이터 패킷 기록과는 다르다.

기본 기록은 **인자·응답 본문·인증정보를 저장하지 않는 메타데이터 중심**으로 구성한다. 예외 메시지에도 입력값이 섞일 수 있으므로 오류 종류·코드와 안전한 요약을 사용한다. 재시작 후 기록을 이어서 읽을 수 있게 하고 저장량에 상한을 둔다.

### 6.2 요구가 있을 때 선택할 기능

| 필요 조건 | 선택 기능 | 구현 기준 |
|---|---|---|
| 특정 도구를 사용하지 못하게 해야 함 | `Visibility` 기반 도구 제한 | 명시된 제한만 적용하고 모든 호출 경로에서 확인 |
| 원격 클라이언트가 내부 Gateway에 접속해야 함 | 인증된 외부 접속 경로 | 클라이언트 지원 방식과 서비스 접근 범위를 함께 확인 |
| 반복 discovery 비용이 실제로 큼 | Provider의 컴포넌트 메타데이터 캐시 | 도구 정의 갱신 요구와 조회 비용을 비교 |
| Gateway 로그만으로 호출 원인을 구분하기 어려움 | upstream RPC 연관 기록 | 공개 확장점을 우선 사용하고 원본 호출 동작을 보존 |

캐시의 대상이 도구 정의인지 실행 결과인지 구분한다. 세션·캐시 관련 기능은 실제 사용하는 프레임워크 API와 연결 대상의 동작을 기준으로 선택한다. [1] 커스텀 확장은 재사용 전에 해당 확장 지점의 호환성을 시험한다.

## 7. 가장 짧은 부트스트랩 순서

**첫 MCP 하나로 실제 호출을 통과시킨 뒤, 검증된 연결 패턴을 다른 MCP에 반복 적용한다.**

| 단계 | 수행할 일 | 다음 단계로 넘어가는 기준 |
|---|---|---|
| **1. 입력 확정** | 핵심 작업, 연결 MCP, 클라이언트 접속 방식, 인증 조건을 정함 | 접속 정보와 실제 성공을 판단할 대표 작업이 정해짐 |
| **2. 최소 연결** | 독립 실행환경에 FastMCP를 구성하고 MCP 하나를 연결 | 원본 도구 정의를 discovery로 받음 |
| **3. 실제 호출** | 원본 스키마로 서비스에 의존하는 대표 도구를 실행 | 서비스 수준의 기대 결과를 얻음 |
| **4. 통합·선별** | 다른 MCP 연결, namespace, 직접/검색 노출 정책을 적용 | 이름 충돌 없이 직접 호출과 검색 후 호출이 동작 |
| **5. 기록 확인** | Gateway와 MCP 통신 기록을 실제 호출 결과와 대조 | 대상 도구·결과·오류를 구분할 수 있음 |
| **6. 최종 클라이언트 확인** | 실제 사용할 클라이언트에서 대표 작업 실행 | 해당 클라이언트부터 서비스까지 전체 경로가 검증됨 |

연결이나 인증에 실패하면 그 경계부터 해결한다. 아직 확인하지 못한 도구 동작을 연결 성공으로 대체하지 않는다. 선택 기능은 기본 호출 경로가 검증된 뒤, 그 기능이 필요한 지점에 적용한다.

구성과 관련 검증은 Git에 함께 보존한다. 실행환경, 자격정보, 로그, 일회성 검증 산출물은 재사용할 소스와 구분한다.

## 8. 재사용 입력과 완료 기준

새 용도로 구성할 때 다음 입력만 새로 정한다. 도구별 상세 스키마는 연결한 MCP에서 받는다.

```text
핵심 작업과 기대 결과:
연결할 MCP의 역할:
MCP별 transport · 접속 정보 · 인증 방식 · namespace:
클라이언트 접속 방식:
도구 노출 방식과 Public 후보:
명시적인 도구 제한 요구:
기록 범위와 필요한 연관 추적:
최종 클라이언트에서 실행할 대표 검증 요청:
```

**완료 기준:** 선택한 MCP를 연결하고, 정책에 맞게 도구를 노출하며, 실제 클라이언트의 대표 작업을 성공시키고, 필요한 로그로 그 호출을 설명할 수 있다.

비용 판단에는 **구현 시간, 의존성과 추가 코드의 유지 비용, 도구 선택·호출의 왕복, 연결 서비스의 이용 요금**을 함께 포함한다. 프레임워크의 기존 기능으로 이 완료 기준을 충족하면 그 구성을 다음 부트스트랩의 기준으로 삼는다.
